# AtomUI 6.2.7 migration guide

[简体中文](6.2.7-api-changes.zh-CN.md)

6.2.7 corrects the startup configuration boundary. The public `AppBuilder.UseAtomUI` signature and the minimum
Avalonia dependency (12.1.4) are unchanged; Release product packages still target net8.0 and net10.0.

## Quick reference

| Area | 6.2.6 | 6.2.7 |
| --- | --- | --- |
| `UseAtomUI(configure)` | Executes configuration during registration, before platform initialization | Only registers configuration; executes it on the UI thread after platform setup, before Application construction |
| Configuration exceptions | Throw from the `UseAtomUI` call | Throw unchanged during platform setup, normally inside `StartWithClassicDesktopLifetime` |
| Indirect AvaloniaObject construction | Can create the Dispatcher before its native backend and disturb timer deadlines | Runs after the platform has established the Dispatcher |
| Generated registration groups | Include the 6.2.6 assembly identity | Include the 6.2.7 assembly identity; rebuild generated consumers |

## Configuration and exception timing

Keep the normal entry point:

```csharp
AppBuilder.Configure<GalleryApplication>()
          .UseAtomUIPlatformDetect()
          .WithAtomUIDefaultOptions()
          .UseAtomUI(GalleryApplication.Configure)
          .StartWithClassicDesktopLifetime(args);
```

The configuration callback can keep calling `builder.UseGalleryBase(Module.Configure)`. Ordinary module configuration
may indirectly construct an AvaloniaObject-derived data repository. Application construction and AtomUI commit still
occur later; use initializers or the main-window factory for work requiring committed application resources.

Code following `UseAtomUI` must not depend on the callback having already executed. Keep related configuration inside
the callback or an appropriate later lifecycle hook. Catch startup failures around the complete startup call:

```csharp
try
{
    BuildAvaloniaApp().StartWithClassicDesktopLifetime(args);
}
catch (Exception exception)
{
    LogException(exception);
    throw;
}
```

Configuration runs once per Application instance. Generated `RegisterServices` hookup still commits AtomUI before
`Application.Initialize()`. Design mode and Browser/WASI retain their synchronous Attach fallback.

## Generated registration identities

The existing generator includes the package assembly version in public `ControlPackageGroup_*` names. Increasing the
version therefore changes these identities even though the registration API signatures remain unchanged. Upgrade
AtomUI packages and the Generator together, rebuild applications and custom control packages that consume generated
registration metadata, then republish trimmed/NativeAOT applications. Do not mix old precompiled registration metadata
with the new package set or reference generated group names directly.

These generated identity changes are a binary compatibility change. Package API validation against 6.2.6 must report
them as such; they must not be hidden by compatibility suppressions. No new SDK, target-framework or package-layout
contract is introduced by this startup fix.

The release treats these generated identity changes as intentional binary incompatibility with 6.2.6. It does not
claim package API compatibility with that baseline; the comparison diagnostics remain visible and no ApiCompat
suppression is added. Consumers must rebuild as described above.

## Package validation results

Package API validation against 6.2.6 reports 10 intentional `CP0001` diagnostics: the generated
`ControlPackageGroup_*` identities in `AtomUI.Controls`, `AtomUI.Desktop.Controls`, `AtomUI.Toolkits.GalleryBase`,
`AtomUI.Desktop.Controls.DataGrid` and `AtomUI.Desktop.Controls.ColorPicker` change on both target frameworks. They
are the binary breaks described above and must not be suppressed. Package layout validation against 6.2.6 reports no
differences for all 20 packages, so no `tools/`, `buildTransitive/`, `build/` or target-framework entry changes in
6.2.7.

The [startup lifecycle](../architecture/systems/startup/lifecycle.md) defines the complete ordering, and
[startup verification](../architecture/systems/startup/verification.md) documents the independent process acceptance entry.
