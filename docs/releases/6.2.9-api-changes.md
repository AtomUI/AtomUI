# AtomUI 6.2.9 migration guide

[简体中文](6.2.9-api-changes.zh-CN.md)

6.2.9 restores Splash card shadows and includes the PuHuiTi font package in the normal NuGet release.
Avalonia remains 12.1.4, and Release product packages continue to target net8.0 and net10.0.

## Quick reference

| Area | 6.2.8 | 6.2.9 / migration |
| --- | --- | --- |
| Generated registration groups | Public `ControlPackageGroup_*` names include the 6.2.8 assembly identity | Names include 6.2.9; upgrade related packages together and rebuild compiled consumers |
| PuHuiTi package | Source project exists but is omitted from the release manifest | `AtomUI.Fonts.AlibabaPuHuiTi` is included in the standard release; reference and register it explicitly |
| Splash | Card shadow can be clipped and shares rendering work with animated content | Full shadow is retained and cached separately; Card appearance customization remains available |
| Existing package contracts | net8.0/net10.0 product assemblies and existing build assets | Existing target frameworks, package IDs and build-asset paths remain available |

## Rebuild generated registration consumers

The generator hashes the package assembly identity, including its version, into public
`AtomUI.Generated.*.ControlPackageGroup_*` names. The 6.2.9 version changes these generated names even though the
supported registration method signatures remain the same. Replacing runtime DLLs alone does not rebuild a compiled
consumer's references to those groups.

1. Upgrade related AtomUI packages and any explicit Generator reference to 6.2.9 together.
2. Clean and rebuild applications and custom control packages consuming generated registration metadata.
3. Republish trimmed and NativeAOT applications so dependency analysis uses the new groups.

Continue using supported `UseAtomUI` and package configuration entry points. Do not directly reference generated
group names or mix 6.2.8 compiled registration metadata with the 6.2.9 package set. This is an intentional binary
incompatibility; historical package API comparison must report it rather than suppress it or claim binary compatibility.

## Use the PuHuiTi package

The package contains the existing Alibaba PuHuiTi 3.0 Regular font. Add a reference to
`AtomUI.Fonts.AlibabaPuHuiTi` 6.2.9 and call `UseAlibabaPuHuiTiFont()` in the AtomUI builder, or
`WithAlibabaPuHuiTiFont()` during AppBuilder configuration. Registration alone does not change the default font family;
use `AlibabaPuHuiTiFontConstants.FontFamily` when configuring the desired family.

No font subsetting, additional font weights, or change to the font collection URI or internal family name is included.
Existing packages retain their framework and build-asset checks. Only this explicitly marked, previously unpublished
package may omit a historical baseline after NuGet confirms that its package index does not exist. Once the index exists,
ordinary baseline checks resume; missing versions and network errors are not treated as first publication.

## Splash customization

Existing styles targeting the template's `Border#Card` continue to control its background, corner radius and shadow.
The default theme places a separate cached shadow behind the card and preserves card-content clipping. The opaque
fallback remains square and shadow-free. No Splash public method, property or token is removed.

## Package validation results

Comparison against the 6.2.8 packages reports exactly 10 `CP0001` diagnostics for generated registration groups in
`AtomUI.Controls`, `AtomUI.Desktop.Controls`, `AtomUI.Toolkits.GalleryBase`, `AtomUI.Desktop.Controls.DataGrid` and
`AtomUI.Desktop.Controls.ColorPicker`, across net8.0 and net10.0. No additional API incompatibility or unresolved-reference
diagnostic is reported. The historical API comparison fails for these documented binary incompatibilities; no suppression
is added and this release does not claim binary compatibility with 6.2.8.

All 20 existing package layouts match 6.2.8. PuHuiTi has no historical package and follows the explicit first-publication
rule. No package-layout allowlist change is needed. The supported release workflow can publish this documented binary
break without a historical API baseline; the independent historical comparison above remains part of the release evidence,
and absolute package identity, framework and build-asset validation still apply.
