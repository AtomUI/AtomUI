# AtomUI 6.1.9 API Change Examples

AtomUI 6.1.9 changes one public extension boundary: the MSBuild build-tooling contract. Control, theme and runtime
APIs are unchanged — no control type, property or member was removed in this release. This guide shows the required
migrations from 6.1.8.

Chinese version: [AtomUI 6.1.9 API 变更示例](6.1.9-api-changes.zh-CN.md).

## Quick reference

| Area | 6.1.8 | 6.1.9 migration |
| --- | --- | --- |
| Build tools runtime | `AtomUI.Build.Tasks` shipped as a `netstandard2.0` assembly and ran in-process inside the MSBuild node | Build tools ship as `net10.0` assemblies and run in a single-use process started through the .NET host |
| Build requirement | Any SDK that can load a `netstandard2.0` task assembly | A .NET 10 SDK is required to build a project that references AtomUI |
| Task registration | `<UsingTask ... AssemblyFile="$(AtomUIBuildTasksAssembly)" />` | `<UsingTask TaskFactory="RoslynCodeTaskFactory" ...>` compiling `AtomUI.Build.Tasks.Process.cs` |
| Task invocation | Tasks took only their feature-specific parameters | Tasks additionally require `TaskAssembly` and accept `DotNetPath` |
| Custom build-task overrides | `AtomUIBuildTasksSourceAssembly`, `AtomUIBuildTasksShadowKey`, `AtomUIBuildTasksShadowRoot`, `AtomUIBuildTasksShadowDirectory` | Removed; set only `AtomUIBuildTasksAssembly` to the `net10.0` task assembly |
| Tool package layout | `tools/netstandard2.0/AtomUI.Build.Tasks.dll` | `tools/net10.0/AtomUI.Build.Tasks.dll` plus its runtime config and dependencies |

## Build a project that references AtomUI with the .NET 10 SDK

The AtomUI MSBuild integration no longer loads its task assembly in-process. The SDK-compiled adapter starts a
single-use .NET process through the .NET host to run the real tasks, so the host must be able to run `net10.0`
assemblies. Building any project that references AtomUI therefore requires a .NET 10 SDK. Product target frameworks
are unchanged — an application may still target `net8.0`.

Before (6.1.8): any SDK able to load a `netstandard2.0` task assembly could build the project.

After (6.1.9): the build machine must have a .NET 10 SDK installed, even when the application targets `net8.0`.

## Custom source builds: update the build-task path override

Normal NuGet consumers do not set a build-task path. Custom source builds and test harnesses that point at a
repository task assembly must target the `net10.0` output. The shadow-copy properties are removed and must not be set.

#### 6.1.8

```xml
<PropertyGroup>
  <AtomUIBuildTasksAssembly>$(RepoRoot)/tools/netstandard2.0/AtomUI.Build.Tasks.dll</AtomUIBuildTasksAssembly>
</PropertyGroup>
```

#### 6.1.9

```xml
<PropertyGroup>
  <AtomUIBuildTasksAssembly>$(RepoRoot)/tools/net10.0/AtomUI.Build.Tasks.dll</AtomUIBuildTasksAssembly>
</PropertyGroup>
```

`AtomUIBuildTasksSourceAssembly`, `AtomUIBuildTasksShadowKey`, `AtomUIBuildTasksShadowRoot` and
`AtomUIBuildTasksShadowDirectory` no longer exist. The content-keyed shadow staging and the
`AtomUI.BuildTasks.ShadowKey.props` stamp are gone: the adapter no longer holds a loaded task DLL for the lifetime of
the build node, so no shadow copy is required.

## Direct task invocations: supply `TaskAssembly` and `DotNetPath`

Code that invokes AtomUI tasks directly, outside the shipped `.targets` files, must pass the task assembly path and
optionally the .NET host path. Every task now derives from a shared isolated base that requires `TaskAssembly`.

#### 6.1.8

```xml
<AtomUI.Build.Tasks.CollectAxamlUsageTask
    AxamlFiles="@(AvaloniaXaml)"
    OutputFile="$(IntermediateOutputPath)usage.json" />
```

#### 6.1.9

```xml
<AtomUI.Build.Tasks.CollectAxamlUsageTask
    TaskAssembly="$(AtomUIBuildTasksAssembly)"
    DotNetPath="$(DOTNET_HOST_PATH)"
    AxamlFiles="@(AvaloniaXaml)"
    OutputFile="$(IntermediateOutputPath)usage.json" />
```

The registered task type names are unchanged. The `<UsingTask>` registration now uses `RoslynCodeTaskFactory` to
compile the process adapter from `AtomUI.Build.Tasks.Process.cs`; downstream consumers normally rely on the shipped
`buildTransitive` assets and need no change.

### Rebuild compatibility boundary

Do not mix 6.1.8 task assemblies, shadow directories, or cached `AtomUI.BuildTasks.ShadowKey.props` files with 6.1.9
build assets. Clear stale tool outputs and rebuild against the 6.1.9 packages; do not pre-stop the IDE or disable node
reuse, because the new execution path does not depend on either.
