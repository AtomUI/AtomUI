# AtomUI 6.2.2 API Change Examples

Despite its patch version, AtomUI 6.2.2 includes breaking changes to target frameworks, control-package registration, theme discovery, platform metadata and shipped build assets. This guide describes migration from 6.2.1. Applications should upgrade their SDK and target framework before upgrading packages. Third-party control packages must then be rebuilt with the matching generator.

Chinese version: [AtomUI 6.2.2 API 变更示例](6.2.2-api-changes.zh-CN.md).

## Quick reference

| Area | 6.2.1 | 6.2.2 migration |
| --- | --- | --- |
| Product target framework | `lib/net8.0` and `lib/net10.0` | Only `lib/net10.0` is shipped. Target `net10.0`, use a .NET 10 SDK, and rebuild consumers. Browser applications target `net10.0-browser`. |
| Registration ABI | `AotTrimRegistration`, Unit/Plan/Sidecar pipeline and generated linked-registration entry | Use the generated TypeMap registration pipeline. Rebuild and republish third-party control packages with the v6.2.2 generator; old binaries cannot register through the new ABI. |
| Theme discovery and schema | `ControlThemeProviderAttribute`, `IControlThemeProvider`, owner/reference/string asset metadata and earlier `ControlPackageRegistration` constructors | Use `IControlThemesProvider` and generated registration. Recreate custom schema descriptors with actual exported `Type` keys, token owners and semantic bindings. |
| Build integration | `AtomUI.LinkedRegistration*.props/targets`, `.atomui-link.json` and `AtomUI.Generator.LinkedPublish` | Remove custom imports and references to retired files. `buildTransitive/AtomUI.Registration.targets` resolves the current generator, worker and Browser backend. |
| Theme platform metadata | `AtomUISupportedOSPlatforms`, `AtomUIUnsupportedOSPlatforms` and project theme-path lists | Put standard `SupportedOSPlatformAttribute` / `UnsupportedOSPlatformAttribute` declarations on the relevant control or resource CLR type. |
| Generated token API | Resource-key types for controls without an own token and old DataGrid / WindowTitleBar token enum numbers | Replace references to removed keys, rebuild generated token clients, and do not persist token enum numbers across versions. |

## 1. Move applications and libraries to .NET 10

The production package target framework changes from `net8.0` to `net10.0`; `lib/net8.0` is removed. A `net8.0` project cannot reference the v6.2.2 product packages. The build machine also needs a .NET 10 SDK. This is a product TFM change, beyond the .NET 10 build-tool requirement introduced in 6.1.9.

Before:

```xml
<TargetFramework>net8.0</TargetFramework>
<PackageReference Include="AtomUI.Desktop.Controls" Version="6.2.1" />
```

After:

```xml
<TargetFramework>net10.0</TargetFramework>
<PackageReference Include="AtomUI.Desktop.Controls" Version="6.2.2" />
```

Move every application and library that directly references an AtomUI product package. Browser applications use `net10.0-browser`; verify Browser trimming with the supported SDK and linker described in [AOT and trimming](../architecture/foundations/aot-and-trimming.md). Rebuild all consumer binaries after the TFM change.

## 2. Rebuild third-party control packages for TypeMap registration

The old `AotTrimRegistration`, `AotTrimRegistrationPlanRegistry`, `AotTrimControlPackageRegistrationBuilder`, `AotTrimUnitAttribute` / `AotTrimGeneralUnits`, and `ControlPackageRegistrationEntryAttribute` API and generated ABI are removed. The Unit, application usage, Sidecar, Plan and whole-package fallback paths are no longer read or executed. A third-party package compiled against that ABI cannot be made compatible by changing only the consuming application's version.

Keep the application's normal package entry calls, such as `UseAtomUI()` and `UseDesktopControls()`. For a third-party package, use a v6.2.2 reference and the [third-party control-package guide](../guides/theming/third-party-control-packages.md) to rebuild its public package entry and theme provider. Republish the rebuilt package, then rebuild the application. `UseAllDesktopControls()` is removed; replace it with `UseDesktopControls()`. Applications that used the former to retain dynamically created controls in a trimmed publish must declare those dynamic types through normal .NET trimming roots and verify the published application. There is no equivalent full-package registration switch.

The v6.2.2 generator emits package markers, conditional TypeMaps, registration fragments and resource factories. Package authors do not manually maintain an AOT control list, a Sidecar or a publish-mode branch.

The current package model registers controls, theme assets, semantic descriptors and resource factories together. If custom code constructs `ControlPackageRegistration` directly, pass the new `IEnumerable<ControlThemeResourceRegistration>` argument in addition to semantic descriptors; its earlier constructors are gone. Registration validates the entire package before committing it. After a failed `AddControlPackage`, create a new builder for a retry rather than reusing the failed one.

## 3. Update theme discovery and schema extensions

The unused single-theme `ControlThemeProviderAttribute` and `IControlThemeProvider` contracts are removed. Implement the package-level `IControlThemesProvider` contract and let the generated registration entry supply the resource factories. The independent typed-template capability of `BaseControlTheme` remains available.

`ControlThemeAssetDescriptor` now needs an `AssetId`, actual exported theme types, required token-owner identities and semantic theme bindings. Its former owner/reference/string constructor and `OwnerIdentity`, `ReferencedControlIdentities` and `SemanticPart` properties are removed. `ControlThemeSemanticPartDescriptor` now takes `Type targetType` rather than a string name and exposes `TargetType` rather than `TargetTypeName`. Code that constructs these descriptors must move to the current signatures or, preferably, let the generator derive them from AXAML.

Cross-asset `StaticResource` references must have a provable source during ordinary compilation. Replace a resource name that depended on directory inference with a normal explicit `ResourceInclude` or a package-core/provider export. The old `AtomUIPackageSharedTheme` and `AtomUIPackageSharedThemePaths` switches no longer provide ownership. Keep package identity stable because it scopes resources and registration.

### Generated token keys and enum values

The TypeMap generator no longer emits public token-key, token-resource-extension and token-holder types for controls without an own token, whether the control is abstract or concrete. The ApiCompat gate lists affected names in `AtomUI.Controls`, `AtomUI.Desktop.Controls` and `AtomUI.Desktop.Controls.ColorPicker`; examples include `ItemsControlTokenKey`, `AbstractAutoCompleteTokenKey`, `FormValidateFeedbackTokenKey` and their corresponding `*TokenResourceExtension` types. Rebuild C# and AXAML that referenced these names. Use a supported control key where the value belongs to another control, or define an application-owned token/resource key for a custom abstraction. There is no universal renamed type.

Adding pagination and caption geometry tokens changes numeric values of existing `DataGridTokenKey` / `DataGridTokenKind` and `WindowTitleBarTokenKey` / `WindowTitleBarTokenKind` members. Member names remain the stable way to refer to a token, but numeric values serialized as integers or embedded in precompiled binaries must be regenerated for 6.2.2.

## 4. Remove retired build assets and migrate platform declarations

Remove custom imports or references to `AtomUI.LinkedRegistration.props`, `AtomUI.LinkedRegistration.targets`, `AtomUI.LinkedRegistration.SidecarConsumer.targets`, `.atomui-link.json` and `AtomUI.Generator.LinkedPublish`. The v6.2.2 packages include `buildTransitive/AtomUI.Registration.targets`; ordinary package consumers do not add a generator analyzer manually. The generator and dependencies are placed in `tools/netstandard2.0` and `analyzers/dotnet/cs`, the worker in `tools/net10.0`, and the Browser backend in `tools/typemap`. Product assemblies stay under `lib/net10.0`.

`AtomUI.Controls` now carries the registration build assets and tool dependencies for direct package consumers. Do not strip those `buildTransitive/` or `tools/` entries when repackaging it.

Direct calls to generated `CompiledAvaloniaXaml.!AvaloniaResources.Build/Populate` methods for `WindowDrawnDecorationsTheme.axaml` must also be removed. This theme now has a normal internal resource CLR class. `UseDesktopControls()` provides the package theme registration; custom resource imports can use the normal `avares://AtomUI.Desktop.Controls/Window/Themes/WindowDrawnDecorationsTheme.axaml` URI. Do not call the internal class or compiler-generated method names.

### Theme platform declarations

Theme platform availability now follows standard .NET declarations on the actual control or resource CLR type. The custom `AtomUISupportedOSPlatforms` / `AtomUIUnsupportedOSPlatforms` metadata and `.csproj` theme-path exclusion lists are removed. For example, when only a theme resource is platform-specific, annotate its resource type rather than disabling the reusable control:

```csharp
using System.Runtime.Versioning;
using Avalonia.Controls;
using Avalonia.Markup.Xaml;

namespace Acme.Controls.Themes;

[SupportedOSPlatform("windows")]
public partial class WindowsOnlyThemeResources : ResourceDictionary
{
    public WindowsOnlyThemeResources() => AvaloniaXamlLoader.Load(this);
}
```

```xml
<ResourceDictionary xmlns="https://github.com/avaloniaui"
                    xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
                    x:Class="Acme.Controls.Themes.WindowsOnlyThemeResources">
    <!-- Platform-specific theme resources. -->
</ResourceDictionary>
```

Give an AXAML `ResourceDictionary` or `ControlTheme` that needs its own availability domain a normal `x:Class` resource identity. Rebuild third-party packages with the v6.2.2 generator. Do not retain the removed metadata as a second platform list; it is not read. The Browser supported surface is unchanged by this declaration migration.

## 5. Validate the migration

1. Upgrade the SDK, application TFM and AtomUI package references together.
2. Rebuild third-party control packages with v6.2.2 and remove old registration and theme metadata.
3. Remove custom imports and references to retired build assets; use explicit resource includes and standard platform declarations.
4. Clean stale `obj`/generated outputs, rebuild, and verify normal startup, theme switching and popup templates.
5. If publishing with trimming or NativeAOT, publish again and exercise the used controls. Browser trimmed/AOT publishing retains the pinned SDK/toolchain requirement; desktop publishing accepts compatible later .NET 10 patch toolchains.

## Release-gate audit record

ApiCompat against v6.2.1 reports 13 removed-target-framework diagnostics (`PKV006`), 186 removed types (`CP0001`), 11 removed members (`CP0002`) and 136 changed enum constants (`CP0011`). The removed-type set consists of the old registration/theme-discovery ABI, linked-registration generated types and generated token types for controls without an own token. The member set covers the constructors and properties described above, `UseAllDesktopControls()` and generated AXAML entry methods. The constant set belongs to DataGrid and WindowTitleBar token enums. These diagnostics are expected evidence of the break; they are not suppressed by the package-validation gate.

Package-layout validation records 105 exact added or removed paths across 14 packages in the [v6.2.1 layout allowlist](../../scripts/verification/package-layout-allowlist.json). The paths cover the removed `lib/net8.0` assets, retired linked-registration assets and the new TypeMap/tool payloads. These acknowledgements identify intentional breaks; they do not make old binaries or `net8.0` consumers compatible.
