# AtomUI 6.2.8 migration guide

[简体中文](6.2.8-api-changes.zh-CN.md)

6.2.8 fixes DashedBorder scaling, Windows 10 CSD borders and repeated ImagePreviewer rotation, and broadens
TypeMap toolchain support. Avalonia remains 12.1.4 and Release product packages still target net8.0 and net10.0.

## Quick reference

| Area | 6.2.7 | 6.2.8 / migration |
| --- | --- | --- |
| Generated registration groups | Public `ControlPackageGroup_*` names include the 6.2.7 assembly identity | Names include 6.2.8; upgrade packages together and rebuild compiled consumers |
| Window token enum values | Existing own-token slots precede the new frame-border tokens | Name ordering inserts two new slots; recompile custom themes and resource consumers and use named members |
| Browser TypeMap publishing | Requires SDK 10.0.300, ILLink 10.0.8 and WASM tasks 10.0.10 | Defaults to .NET 10 and later stable versions, using SDK-selected tools and retaining conversion/output validation |
| Modern desktop TypeMap tools | Matching target framework with a 10.0.8 minimum | Matching target framework with a 10.0.0 minimum |
| Build-tool runtime | Uses `LatestPatch` roll-forward | Uses `Major`; a later SDK environment need not install the original .NET 10 tool host |
| Control methods and package layout | Existing control methods, package IDs, net8.0/net10.0 and build-asset paths | No existing control method, target framework or build-asset path is removed; Window token enum values change as described below |

## Rebuild generated registration consumers

The generator hashes the package assembly identity, including its version, into public
`AtomUI.Generated.*.ControlPackageGroup_*` names. Upgrading the package version changes these generated names even
though the supported registration method signatures remain the same. A precompiled consumer referencing an old group
cannot bind to the new group merely by replacing its AtomUI DLLs.

1. Upgrade related AtomUI packages and any explicit Generator reference to 6.2.8 together.
2. Clean and rebuild applications and custom control packages that consume generated registration metadata.
3. Republish trimmed and NativeAOT applications so their dependency analysis uses the new registration groups.

Use the supported `UseAtomUI` and package configuration entry points. Do not reference generated group type names
directly or mix 6.2.7 precompiled registration metadata with the 6.2.8 package set. No startup callback or application
resource migration is added on top of 6.2.7.

This is an intentional binary incompatibility with 6.2.7. Package API comparison must report the generated identity
changes, without suppressions or a claim of full binary compatibility. Package layout is checked separately.

## Recompile Window token consumers

The new `FrameBorderActive` and `FrameBorderInactive` tokens are inserted into the generated own-token enums in name
order. Existing names stay available, but their numeric values change:

| Member | `WindowTokenKind` 6.2.7 → 6.2.8 | `WindowTokenKey` 6.2.7 → 6.2.8 |
| --- | --- | --- |
| `FrameShadows` | 3 → 5 | -4 → -6 |
| `FullscreenHeaderFramePadding` | 4 → 6 | -5 → -7 |
| `FullscreenPopoverShadows` | 5 → 7 | -6 → -8 |
| `SystemBarColor` | 6 → 8 | -7 → -9 |
| `TitleBarHeight` | 7 → 9 | -8 → -10 |

Rebuild custom themes, compiled AXAML dictionaries and code that uses these enums. Enum constants are embedded into
compiled consumers, so replacing the runtime DLL alone can select the wrong resource. Continue to use named values
such as `WindowTokenKey.FrameShadows`; do not persist or hard-code their integer values. If an application already
stores token integers, migrate them using the original member names and the table above. Global token slots and the
first three Window own-token slots are unchanged.

## TypeMap toolchain support

Modern TypeMap publishing defaults to .NET 10 and later stable versions. Browser publishes no longer require a specific
SDK feature band, servicing version, full linker build string or WASM task version. Keep the SDK-selected toolchain;
there is no need to configure a backend path or enable a compatibility switch for this change.

The Browser backend still validates the actual official linker identity, Mark/Sweep/Output ordering, registration ABI,
converted maps and the files consumed by AOT or bundling. Tool versions and file contents remain part of the incremental
signature. Default admission of a future version does not mean every future linker implementation has been tested.
Real conversion, ABI or output failures stop publishing and require adaptation.

Modern desktop trimmed/NativeAOT publishing still requires tools matching the target framework. The minimum version
is now 10.0.0, where TypeMap was introduced. The separate .NET 8 backends and the bridge for consuming net8-only
packages retain their documented SDK/runtime/platform limits.

## Control fixes

DashedBorder keeps its sizing and rounded child clipping while preparing scale-dependent clips before rendering.
Windows 10 CSD windows regain their missing top frame border at one physical pixel, including high-DPI active/inactive
states. ImagePreviewer keeps rapid repeated rotation continuous. No control method signature changes; Window token
consumers must follow the rebuild requirements above. Applications with custom Window templates should verify that
they retain the standard drawn-decorations overlay.

## Package validation results

Comparison against the 6.2.7 packages reports 10 `CP0001` diagnostics for generated registration groups in
`AtomUI.Controls`, `AtomUI.Desktop.Controls`, `AtomUI.Toolkits.GalleryBase`, `AtomUI.Desktop.Controls.DataGrid` and
`AtomUI.Desktop.Controls.ColorPicker`, across net8.0 and net10.0. It also reports 20 `CP0011` diagnostics for the five
Window members in both token enums on both frameworks, matching the migration table above.

These are documented binary incompatibilities; the API baseline comparison fails and is not described as passing.
The comparison reports no additional API incompatibilities or unresolved-reference diagnostics. No ApiCompat
suppression is added. All 20 package layouts and their expected Release target frameworks pass separate validation
against 6.2.7; no package-layout allowlist change is needed.
