# AtomUI 生态注释书写规范

**版本 1.0**

本规范适用于 AtomUI 生态仓库中的 C#、AXAML、测试和构建脚本。公开声明的注释记录使用契约，内部实现的注释记录维护代码所需的原因与约束。

## 1. 内容原则

1. **每句话都应有用。** 删除一句后，如果读者仍能凭声明、相邻代码和其余注释作出同样的使用或维护判断，就删除这句。成员名、签名和代码已清楚表达的信息无需复述。
2. **摘要通常一句。** 先说明对象的用途或可观察行为。只有生效条件、特殊值、时序、副作用等会影响使用时，才补充说明。内容写到足以正确使用为止。
3. **注释必须自包含。** 源码注释不得引用仓库 `docs/` 下的文件、章节或对应网页，也不得只写规范章节编号。理解当前声明或实现所需的条件、行为和例外，直接在该处写全。可引用代码符号，同时写清符号之间的关系。
4. **同一契约只完整说明一次。** 把说明放在承担契约的声明上，其他入口按需继承或关联。行为变化时同步更新注释，清理已失效的说明和注释掉的旧实现。
5. **公开 API 注释统一使用英文。** 内部实现注释默认使用英文。术语沿用仓库已有名称，确保同一概念在不同模块中表达一致。

## 2. C# XML 注释排版

- 使用 `///`，与声明同级缩进，置于声明及其特性列表之前。`///` 与标签或正文之间留一个空格。
- **块级标签的开始标签、正文和结束标签分别占行。** 即使正文只有一句或一个短语，也必须展开。此规则适用于 `<summary>`、`<param>`、`<typeparam>`、`<returns>`、`<value>`、`<exception>`、`<remarks>`、`<example>` 等带正文的标签。
- 同级标签连续书写。较长正文按语义折行，多段内容使用 `<para>`，多行代码使用 `<code>`。嵌套块级标签缩进一级。
- `<see />`、`<paramref />`、`<typeparamref />` 和 `<c>…</c>` 随正文行内书写。独立的 `<inheritdoc />` 单独占一行。自闭合标签的 `/>` 前留一个空格。
- 标签按摘要、泛型参数、参数、返回值或属性值、异常、补充说明、示例的顺序组织。同类参数按声明顺序书写，名称与签名一致。代码引用必须能解析到正确目标。

```csharp
/// <summary>
/// Template for separators between adjacent children, or <see langword="null" /> to omit them.
/// </summary>
```

## 3. 公开 API 注释

供外部使用的类型、成员和枚举值，以及供外部派生类使用的扩展点，必须提供 `<summary>` 或可解析的 `<inheritdoc />`。内部成员承担跨模块契约时，也应提供 XML 注释。`partial` 类型的类型说明放在主声明上。

| 对象 | 应写的内容 |
|---|---|
| 类型、构造函数 | 类型承担的职责。构造有重要前置条件、所有权转移或可观察副作用时，写明相应行为。 |
| 属性、字段、枚举值 | 值控制什么或表示什么。按实际契约说明单位、有效范围、特殊值和回退。布尔属性应明确 `true` 时启用哪种行为。 |
| 方法 | 调用后发生什么。会影响调用的线程要求、操作顺序、失败结果或状态变化必须写清。`Try*` 方法说明成功和失败条件，以及两个分支下 `out` 值的含义。 |
| 异步方法 | 任务完成有特定含义时，说明它代表请求已接受、状态已提交，还是操作已结束。取消可能影响已提交状态时，说明其行为。 |
| 事件 | 触发原因和时机。涉及状态变化时，说明事件在状态提交前还是提交后触发。可取消时说明取消会阻止什么。 |
| 可重写成员 | 调用时机、调用 `base` 的要求，以及重写者必须维持的状态或生命周期约束。 |

把最影响正确使用的信息放在摘要中。`<param>`、`<typeparam>`、`<returns>` 和 `<value>` 用于补充签名未表达的语义。使用参数标签时，同类参数逐一覆盖。`<exception>` 记录调用方可以依赖的异常及触发条件。`<remarks>` 和 `<example>` 用于补充复杂约束或不易推断的用法。

重写或接口实现完整沿用原契约时，可使用 `<inheritdoc />`。行为、限制或副作用有差异时，在当前声明处完整说明实际契约。

## 4. 控件公开样式属性

**每个控件对外开放的样式属性都必须逐项注释。** 范围包括外观、尺寸、间距、排版、状态样式，以及应用方可设置的子项属性和附加属性。

1. **设置位置与作用范围。** 写清值应设在控件、子项还是其他元素上，以及实际影响的区域或行为。容易混淆的属性应说明各自的作用，例如容器内边距与子项间距。
2. **生效条件。** 属性只在特定形态、尺寸档、状态或模式下生效时，必须说明。显式值在某些条件下会被忽略、约束或替代时，写明条件与结果。
3. **特殊值、默认与回退。** `null`、`0`、空值或其他特殊值会改变行为时，说明实际语义。未设置或清除显式值后，回退到主题、Token 或预设值时，应说明来源及条件。会影响用法的覆盖规则也应写清。
4. **说明归属。** 有 CLR 包装属性时，完整说明写在包装属性上，公开注册字段简短标识对应属性。没有包装时，由注册字段承担完整说明。附加属性说明值承载元素、读取方及适用的传播范围。派生控件若改变继承属性的作用范围、生效条件或回退，应在该控件处说明差异。

`Space.Padding` 的注释可以直接交代测量边界和相关属性。

```csharp
/// <summary>
/// Insets the child layout area from the inner edge of the border.
/// Use <see cref="ItemSpacing" /> and <see cref="LineSpacing" /> to set gaps within that area.
/// </summary>
```

## 5. 主题契约

### 5.1 Design Token

**每个手写 Token 定义都必须说明该值影响哪里、改变什么，以及在什么条件下生效。**

- **全局 Token** 说明其设计角色和作用范围。Seed 说明它驱动的设计选择，Map 说明派生值承担的用途，Alias 说明它对应的消费语义。取值相同的 Token，各自记录其设计角色。
- **控件 Own Token** 说明控件区域、视觉属性或布局边界，以及适用的状态、尺寸档或模式。选中、活动、悬停和焦点等容易混淆的状态应明确区分。
- **语言专属 Token** 说明该值在语言中的含义，以及主要影响哪些派生结果。保留中的 Token 说明保留理由及当前生效情况。
- **取值与单位** 由实际声明和规则维护。注释说明取值语义、重要的单位和边界。随主题变体变化的值，说明适用条件和来源。

```csharp
/// <summary>
/// Background of the active dropdown option, for example during keyboard navigation.
/// </summary>
```

### 5.2 设计语言

**每种设计语言的入口和关键取值规则都必须注释。** 类型说明设计语言负责哪套取值规则，规则说明哪些输入会改变结果，以及求值如何进行。

- 风格、明暗、密度和设备形态存在影响使用的差异或限制时，在相应声明处写清。稳定 ID、支持集合和默认项以实际声明为准。
- 种子与派生规则说明可调输入及其主要影响。存在规则叠加、显式值冻结或中间结果复用时，写清顺序及后续规则读取的结果。
- 控件取值规则存在语言特有的映射、刻意保留的差异或有条件的回退时，在对应分支或赋值组旁说明理由。同一理由覆盖一组赋值时，集中写一次。

### 5.3 Semantic Part

**每条 `[SemanticPart]` 声明上方必须有对应的注释。** 说明它代表的用户可识别区域、何时存在，以及使用哪个公开专用 Style 定制。

- 可选、重复、按状态替换或跨视觉根的部件，说明这些特征怎样影响命中。重复部件写清以什么为单位出现。
- `ContractType`、`Cardinality`、`Since` 等由声明表达。注释补充调用方需要理解的实际行为。复杂 `SelectorRoute` 需要维护说明时，写清为什么必须跨越相应宿主、模板或视觉根。
- 定制入口使用生成的专用 Style 名称。当前模板层级、节点名称和临时容器仅在维护需要时说明。

```csharp
// A separator is created between adjacent children when SplitTemplate is set.
// SpaceSeparatorStyle applies to every separator.
```

## 6. 实现、AXAML、测试与脚本注释

- **实现注释**放在受约束的语句或代码块上方，说明为什么必须保持某个顺序、边界或兼容行为。涉及绑定、订阅、缓存或资源宿主时，写清有实际影响的所有权、替换和释放时机。必须在代码中建立主题绑定时，注明 ControlTheme 无法等价表达的具体原因。
- **AXAML 注释**紧贴相关元素，解释选择器路径、资源归属或布局约束。诊断器识别的标记保留固定形式。`<!-- layout -->` 用于符合规则的布局常量，`<!-- shared: reason -->` 说明跨控件共享的原因，`<!-- owner: reason -->` 紧邻对应 `ControlTheme` 并说明为何必须跟随宿主。
- **测试注释**说明为何必须保留某个输入、操作顺序或边界断言。**脚本注释**说明难以从命令看出的前置条件、影响范围和副作用。
- **临时处理**说明适用的平台、版本或触发条件，以及何时可以移除。`TODO` 和 `FIXME` 写明剩余事项及完成或移除条件。工单可补充证据，必要背景仍须直接写在本处。
- **生成代码**的注释在生成器、模板或源声明中维护。

## 7. 审查标准

新增公开契约或修改既有行为时，注释与代码一并审查。控件按对外可设置的样式属性逐项核对，主题按实际声明逐项核对。

1. **覆盖完整。** 公开样式属性、Design Token、设计语言和 Semantic Part 的必注释项均有对应说明。
2. **契约准确。** 属性设置位置、作用区域、生效条件、特殊值和回退与实际实现一致。读者能区分相近的 Token，理解语言规则的关键顺序，并选对 Semantic Part 的专用 Style。
3. **内容精简。** 逐句删除复述、套话和过期信息。保留删掉后可能造成误用、误改或误判的说明。
4. **排版统一。** XML 块级标签逐行展开，引用有效，注释所需的信息在源码处直接写全。

## 8. 提交前检查

提交包含代码变动时，以 `git diff --cached` 和暂存版本的源码为准，按第 7 节审查本次新增、修改的注释，以及本次声明或行为变动所需的注释。审查范围限于变动代码和受其影响的注释。

发现注释缺失、过期或不符合规范时，修正后核对最终暂存差异。暂存内容在审查后发生变化时，重新检查受影响的范围。检查通过后方可提交。
