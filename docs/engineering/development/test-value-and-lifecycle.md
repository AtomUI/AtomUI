# 单元测试与验收规范

**AtomUI 的常驻单元测试只覆盖框架内核。具体控件及 Gallery 的行为、模板、交互和视觉效果由当次改动验收，
验收后删除临时测试和专用产物。** 新增功能和 Bug 修复仍须建立实现前后证据，并完成清理和最终模块验证。

本文适用于开发者和 AI agent，统一规定单元测试准入、存量清理和交付验收。运行范围、命令与证据有效性见
[按改动影响选择验证](../workflows/affected-verification.md)。根因修复与原始 UX 约束见
[AI 协作规范](../contributing/agent-guidelines.md)。“先写失败测试”和 TDD 均要求有效的实现前后验证，测试去留按本文判定。

## 1. 测试分类与默认处置

按被验证行为的实际所有者和断言确定用途。同一文件中混有不同用途时，逐条判断。

| 类型 | 用途 | 默认处置 |
| --- | --- | --- |
| 常驻内核单元测试 | 验证框架共享机制和基础设施的不变量 | 满足第 2 节准入后保留，按影响范围运行 |
| 临时验收测试 | 验证具体控件行为、视觉效果、Bug 修复、A/B 实验或一次性迁移 | 放在临时位置，验收后清理，不进入常驻测试集 |
| 专项验证 | 验证真实打包消费、NativeAOT、平台行为、性能或压力场景 | 按影响或发布要求运行，临时场景和产物验收后清理 |

用例归属与 xUnit、Headless 等执行方式及测试项目名称无关。专项验证可复用通用执行工具。具体控件的验收用例
及视觉基线按临时生命周期管理，适用于在开发、CI 和发布中执行的验收。现有 runner 按当前映射选测，迁移规则见第 6 节。

### 1.1 临时测试优先（强制）

所有新增功能和 Bug 修复的新增测试，默认先作为临时测试创建。开始写测试前先搜索并复用可表达同一契约的测试。
需要新增常驻测试时按第 2 节审查内核契约。

临时测试按以下顺序选择位置：

1. 能独立运行的复现、探针、A/B 实验或功能验证，放在系统临时目录，例如
   `/private/tmp/atomui-test-<任务标识>/` 或平台对应的临时目录。
2. 必须访问 internal 成员、主题资产、现有 Avalonia Headless 宿主或项目 fixture 时，放在所属测试项目的
   `tests/<测试项目>/Temporary/<任务标识>/` 下。文件头必须注明“临时验证，功能或修复完成后删除”。
3. 临时测试必须被真实编译、发现和执行。禁止通过 `.gitignore`、`Compile Remove`、`Skip`、改名或不进入测试项目
   来制造“已验证”的假象。

默认不得把临时目录加入全局测试选择策略，也不得为了让临时测试看起来正式而新增永久 helper、fixture、资源或
测试项目。需要精确运行时，使用所属项目的直接 filter 或 `run --scope iterate --path ...` 指向临时测试和目标模块。

验收完成后清理临时测试及其专用辅助产物。临时测试在本地工作树执行，提交前从暂存内容中移除。
在交付记录中保存实现或修复前后的验证结论。

## 2. 常驻内核单元测试准入

内核包括主题与 Token 推导、资源及绑定生命周期、本地化、共享数据状态与算法、注册、生成器和构建工具链等基础机制。
按机制的实际所有者定位测试。位于控件程序集中的共享机制也可在其真实边界上独立测试。控件的外观、布局、模板接线、
Semantic PART 在具体模板中的命中、输入与滚动，以及 Gallery 示例行为均属于控件验收。

常驻内核单元测试须同时满足四项条件。保留理由写入交付说明。

1. **契约明确**。指出所属内核机制、稳定不变量，以及违反不变量的具体后果。
2. **独立检错**。能发现编译器、生成器诊断、已有测试或其他确定性检查尚未充分覆盖的真实错误。
3. **长期收益**。保护核心公共路径、曾反复发生的问题，或后果严重、人工难以发现的问题。
4. **成本合理**。使用足以检出故障的最低成本验证方式，结果可重复，并围绕可观察契约设置断言。

全局测试集合默认净新增为零。确需新增常驻内核单测时，交付记录还须说明以下事项。

- 为什么已有测试、编译器、生成器诊断、ApiCompat、真实打包或专项验证不能覆盖该故障。
- 为什么该契约必须进入每次全局测试，而不能保留为按需专项验证。
- 新用例的运行成本、所属模块和触发范围，以及是否已合并或删除同类重复用例。

缺少任一项说明时，不得将测试从临时目录移入全局测试集合。评审者不得以“有回归测试更安全”、Issue 编号、
覆盖率增长或测试已经写好为由批准永久保留。

不满足准入条件的新验证测试，在本次验证完成后删除。已有测试能保护同一契约时，优先复用或合并，
不为每个 Issue 留下一套重复测试。参数化仅减少维护代码时，不得宣称减少了实际执行成本。

先用最小输入直接调用真实内核入口，断言输出、状态转换或资源释放。优先使用可控时间、显式信号和隔离状态。
例如在主题内核验证显式种子值的推导优先级，在控件验收中验证对应样式实际生效。控件用例发现内核缺陷时，
可将符合准入的断言提炼到内核入口，并在原控件场景完成修复前后验证后删除临时用例。

## 3. 控件验收与其他临时测试

控件验收范围由当次改动及其消费路径决定。行为修复复现原始触发条件，主题和视觉变更检查受影响的外观及交互状态。
需要观察像素时，使用同环境、同配置和同状态比较，记录场景及差异结论。截图、像素快照、差分基线、渲染矩阵及
仅供该场景使用的 fixture 在验收后清理。主题 Token 生效的验证方法见[主题生效测试规范](theme-effect-tests.md)。

以下用例同样不进入常驻测试集。

- 为定位当前 Bug 编写的探针、状态打印、A/B 实验和修复方案比较。
- 已完成迁移后逐文件检查旧名称、旧方法或旧目录不存在的过程检查。
- 仅固定私有方法名、局部变量名、文件拆分、代码语句写法的检查。
- 固定普通宣传文案、示例数据、元素顺序或非契约性排版数值的检查。
- 触发条件、断言和故障检测能力已被其他测试覆盖的重复测试。
- 已删除功能、失效需求对应的测试。
- 编译器已经可靠保证的类型存在、成员可访问等重复检查。

跨控件的架构约束可由编译器、生成器或集中审计持续检查，例如禁止特定不安全模式。新增或修改具体控件时，
仍须验收专用 Semantic PART Style、主题绑定边界和实际模板行为。UI 复现须保留原始尺寸、滚动和裁剪条件。

### 3.1 自动准入审计

`python3 scripts/verification/test.py audit` 会拒绝已经明确归类为低价值的常驻测试形态，包括 Gallery 示例源码/文案
快照与页面源码镜像、普通分类/状态/版本宣传文案、手写多语言译文真值表、仓库文件或条目固定总数、README 文案、
完成迁移后的旧符号墓碑、由编译和 ApiCompat 覆盖的精确枚举成员清单，以及固定私有标识符或调用结构的源码检查。
该审计同时进入 plan、focused、CI affected 和显式 full 的 gap 判定，禁止这些测试重新进入全局测试集合。

现有审计规则按路径和意图工作。内核单测可以使用能稳定表达内核不变量的断言；控件几何、样式命中和像素断言
用于临时验收。`Temporary/` 下的用例仍须按第 1.1、4、5 和 9 节真实执行并在交付前清理。
审计通过只证明现有自动规则通过，内核准入和存量迁移仍由评审确认。

### 3.2 本地提交检查

启用仓库的 `scripts/hooks` 后，`git commit` 自动运行 `python3 scripts/verification/test.py audit --staged`。
它读取 Git 暂存内容，拦截 `tests/` 下的 `Temporary/` 文件、带有“临时验证”注释标记的 C# 源码、
已识别的视觉基线，以及指定控件和 Gallery 测试路径中新增或改写的用例。标记检查也覆盖普通内核测试目录和
在现有文件中添加的用例。渲染测试项目也检查分拆的测试片段。未暂存的验收文件可继续用于本地开发。

同一条命令还检查暂存的 `.cs`、`.axaml`、脚本和 MSBuild 文件中的源码注释。规则取自
[AtomUI 生态注释书写规范](code-comment-guidelines.md)，由 `scripts/verification/comments.py` 执行。
暂存内容新增违规时拦截提交，例如对外可见的声明没有 XML 注释、块级标签与正文同处一行、自闭合标签 `/>` 前缺空格、
注释里出现中文、`[SemanticPart]` 上方没有注释、文档注释 XML 不良构、`TODO` 与 `FIXME` 没有写完成或移除条件。既有违规只要求不增加。
`python3 scripts/verification/comments.py list --path <目录>` 列出待办，`check --path <目录>` 要求目录内违规为零，
`diff-check --base HEAD --path <目录>` 证明一批改动只含注释。

仓库使用 `git config --local core.hooksPath scripts/hooks` 启用该目录。Agent 在申请提交审查前应运行同一检查，
保留原有验收和清理记录。遇到拦截应修正暂存内容，提交时禁止跳过 hook 或改写 hook 配置以规避检查。
内核契约的归属、临时测试是否实际执行等事项在评审时按本文核对。

## 4. 新增功能与 Bug 修复执行流程

1. **确认契约与验证范围**：新增功能记录新契约和旧实现缺失的行为；Bug 记录原始触发条件、预期和实际结果。
   先找已有测试能否表达该契约，能复用则不新增重复测试。
2. **建立失败证据**：必要时在临时测试目录编写测试，确认新增功能在实现前不满足目标契约，或 Bug 修复前因目标
   问题失败。编译环境异常、错误断言或测试未被发现不算有效失败证据。
3. **完成根因修复并验证**：同一触发条件、同一有效断言在修复后通过。不能通过删除触发条件、放宽断言、Skip、
   吞错或重试掩盖失败。修改了复现测试的语义时，重新确认它仍能发现原始故障。
4. **决定测试去留**。具体控件的临时用例在验收后删除。共享机制用例可并入现有内核测试，新增常驻用例须满足第 2 节。
5. **清理验证工具**：删除本次临时测试及其专用 helper、fixture、资源和临时工程，停止相关进程；同步清理失效映射。
6. **验证最终工作树**：清理后运行所修改模块的 focused 验证并检查 `git diff --check`。清理前的旧 receipt 不能
   认证清理后的输入；相同最终输入已有有效证据时按 runner 规则复用，不为收尾反复运行。
7. **提交交付记录**：按第 8 节报告验证证据、测试处置和最终模块结果；满足第 9 节全部门禁后才能宣称功能或修复完成。

确实无法自动化复现时，必须说明技术原因，并记录可复查的手动步骤及修复前后证据。单纯耗时、难写或不想
保留测试不是无法自动化的理由。尚无有效失败证据或未完成原始场景复核时，只能报告验证未完成。
修复前后证据须能对应同一问题及相应源码状态；只保留当前变更范围的简短版本/差异说明，不复制无关源码或日志。

UI 验证必须保留原始尺寸、可见滚动条、嵌套滚动、裁剪、布局和交互条件；自动化通过不能替代必要的原始 UX
复核。NativeAOT、平台和资源生命周期专项义务不因普通单测通过或删除临时测试而消失。

## 5. 临时测试的存放与清理

- 能独立运行的复现工程按 1.1 节放系统临时目录，引用当前工作区源码，沿用仓库工具链和依赖。
- 需要内部成员、主题资产或现有 Avalonia 环境时，必须优先放入所属测试项目的 `Temporary/<任务标识>/` 目录，
  并确认测试实际被构建、发现和执行。
- 本次新增的临时测试在验证完成后直接清理，不需要为了普通清理再次请求许可；不得删改用户或其他任务的文件。
- 删除本次测试专用的 helper、数据、fixture、工程、项目引用、截图和差分基线，停止相关进程。可复用的通用工具
  按其实际使用方维护。
- 不用注释、Skip、永久排除编译、改名或归档代替删除，不建立持续积累的临时测试仓库。
- 默认只在交付说明中保留简短验证证据；需要继续调查的截图或日志记录明确用途和位置。不得长期堆积 TRX、dump、
  coverage 等临时产物，也不为保留验证历史而将一次性测试提交后再删除。

临时验证记录对应本次源码和场景。后续改动影响同一行为时，按该次改动重新验收。

## 6. 存量测试清理

本规范合入后适用于新增和改写用例。存量控件测试按控件家族或共享机制分批迁移，可用 6.3.0 发布时的验证结果作为
基线。迁移完成前，现有用例继续按当前验证策略运行。

1. 清点本批控件测试和视觉基线，识别混在其中的内核断言、仍在使用的运行工具和专用 fixture。
2. 删除具体控件的历史行为用例、截图、像素差分及渲染矩阵。满足第 2 节的内核断言优先合并到真实所有者的
   现有测试中。符合准入且仅由控件用例覆盖的内核断言，先验证内核用例能检出同类故障，再删旧用例。
3. 同步清理失去用途的辅助文件、项目和选测映射。对于没有常驻测试的控件区域，验证策略须如实表达编译、
   当次验收和适用专项的实际覆盖。现有 runner 表达不了时，先补齐策略或工具，再迁移对应区域。
4. 在最终工作树验证映射与本批受影响的模块，汇报真实运行范围。零测试、gap、skip 或 pending 按实际状态记录。

存量删除记录使用以下格式；同类项可以成组说明：

```text
删除对象：具体测试或断言
删除原因：控件验收已完成 / 重复覆盖 / 需求已失效 / 编译器已保证
后续验证：内核测试入口 / 适用专项入口 / 受影响时重新验收的控件场景
```

删除低价值测试或已经完成的控件验收用例，无须为凑数补替代测试。

## 7. 执行成本与运行范围

常驻内核测试使用足以验证目标机制的最小环境。控件验收按实际需要使用控件树、渲染后端或真实窗口。实际包消费
通过专项构建与打包验证。保持 UI 隔离、测试状态隔离和原始触发条件。

- 新增常驻用例热运行超过 1 秒，必须复核成本，说明是否存在更低成本的等价方案。
- 超过 5 秒或包含外部 build/pack/publish 时，必须说明常规运行的必要性，优先作为有明确触发条件的专项验证。
- 阈值是复核线，不是自动删除线。耗时采用正常验证输出，区分构建、宿主启动、初始化和用例执行；不为统计额外跑全量。
- 日常修复只做精确复现和模块 focused 验证。全量只在用户明确要求或发版时执行；不得因临时测试清理自动扩大范围。
- 不以测试数量增长、覆盖率上涨或删除比例为目标；评价独立检错能力、反馈时间、稳定性和维护成本。

具体命令和全量失败处理遵循[按改动影响选择验证](../workflows/affected-verification.md)。

## 8. 交付记录

每次新增功能和 Bug 修复必须提供以下记录，写在任务交付说明或 PR 描述中即可，不为每项工作新建永久文档：

```text
验证对象：新增功能的目标契约，或原始故障、触发条件与预期行为
实现/修复前：源码状态、执行命令、预期失败及实际结果
实现/修复后：源码状态、执行命令及结果
测试处置：临时测试已删除 / 合并至…… / 保留……；无新增时说明复用了哪些验证
保留理由：仅保留时填写，说明具体契约、独立检错价值、长期收益与成本
清理结果：临时测试、helper、fixture、资源和进程的处置
最终模块验证：最终工作树的命令、范围、通过数量、耗时和结果
专项与 UX：适用检查及结果；不适用时说明，不得遗漏待完成项
```

手动验证按第 4 节填写步骤与证据，不能伪造测试命令和通过数量。现有缺口、环境限制或待完成专项如实列出。

## 9. 修复完成门禁（硬约束）

作者交付前必须逐项自查；存在代码审查时，审查者按同一条件验收：

- [ ] 有效证明原始故障及根因，完成同一触发条件下的修复前后验证。
- [ ] 新增功能证明实现前后的目标契约差异；新增测试已优先放入临时测试目录并被真实执行。
- [ ] 完成测试去留判定。常驻单元测试属于内核，有满足准入条件的保留理由。
- [ ] 具体控件的行为和外观按受影响场景完成验收，专用视觉基线和截图已清理。
- [ ] 本次临时验证测试及专用辅助产物、工程和进程已清理。
- [ ] 最终分支的临时测试目录为空；全局测试集合的任何净新增都有不可替代性、全局运行必要性和成本说明。
- [ ] 清理后的最终工作树完成对应模块验证，映射有效，无未解决的失败或证据缺口。
- [ ] 所有适用的原始 UX、AOT、平台、资源生命周期专项义务已完成。
- [ ] 交付记录完整，实际运行范围和验证结果表述准确。

任一项未完成，必须报告“功能或 Bug 修复未完成”及具体缺项，不得以单测全绿、编译成功或代码已改代替验收。
测试数量没有增加、临时复现代码已经删除不构成验收失败；验证缺失、无理由保留临时测试或未清理才构成缺项。

本文定义工程与审查门禁，不表示现有 CLI 已自动判定测试价值或检查全部清理事项。runner 成功仅是执行证据，
作者和审查者仍必须完成上述检查；不得把 CLI 退出码 0 等同于满足全部 Bug 修复要求。
